\section{Problem Statement}
For this assignment we were given sample python code which simulates out of order exeuctions using the tomasulo algorithm. This algorithm includes reorder buffer (ROB), register alias table (RAT), a load-store-queue, reservation stations, functional units, and pipelining. All of these features come together to facilitate out-of-order execution. We were tasked with modifying this code to allow for multiple instructions to be executed during one clock cycle. Additionally I implemented allowance for commiting multiple instructions per clock cycle, as that is something that we talked about during the lecture in which we went over a practice problem closely related to this homework.

Additionally the input and output described in the assignment pdf is different from what is currently implemented. Specifically the existing input cannot take in register values, number of reservation stations (RS), cycles in EX, cycles in MEM, number of functional units (FUs), ROB entries, and issue width from the input text file. The output does not output the final register and non-zero memory values. Therefore I added this functionality into the existing code.

\section{Expanding Issue Width}
For this assignment we expand issue width to be able to issue and commit up to 4 instructions in one cycle. Expanding the amount of commands which can be issued in a cycle can be done directly through main by modifying the issue stage (lines 90-105 in main.py). This is done by adding a for loop of range issue\_width, and issuing an instruction each iteration as long as the issuing is valid (i.e. there is an open RS for the instruction) and there are still instructions to be issued.

Expanding issue with for commits as well is done through the |commit| function in commit.py. Again this is done simply by adding a for loop of range issue\_width, and committing an instruction each iteration as long is the head pointer of the ROB is pointing at a instruction that is ready to commit. Since instructions must commit in order, as soon as the instruction which the head pointer points to (implemented as |ROB[0]|) is not ready to commit, we break from the fop loop so no further operations are committed and the current operation is not removed from the ROB.

\section{Input Parser}
An input parser is used to be read from the input file the structure of our o3-simulator, that being the number of RS' for each instruction type (integer adder, FP adder/multiplier, and load/stores), The number of cycles each FU takes to execute and store in memory (memory is only impacted by load/store instructions, all other instructions take 0 cycles in the MEM pipeline stage), number of ROB entries, the issue width, and initial memory and register values. This is implemented in input\_parser.py though standard parser methods (i.e. reading the input line by line and using regular expressions to parse values). Parsed values are placed into the |SimulationInput|. A |UnitConfig| class is also used, which |SimulationInput| derives values from to save the full information of the program. A |SimulationInput| instance is returned to main through |read_input(filename)| (function in input\_parser.py) containing all the information required to run the simulation with the parameters given in the input file.

\subsection{test\_case.txt}
The first test case we look at is the one given to us in test\_case.txt, which has the following parameters for the input (issue width is not given as we change it to show how it impact runs):
\begin{enumerate}[nosep, wide, labelindent=0pt]
  \item[] \textbf{Int. Adder:} 4 RS, 1 Cycle in EX, 1 FU
  \item[] \textbf{FP Adder:} 3 RS, 4 Cycles in EX, 1 FU
  \item[] \textbf{FP Mult.:} 2 RS, 15 Cycles in EX, 1 FU
  \item[] \textbf{Load/Store:} 5 RS, 1 Cycle in EX, 5 Cycles in Mem, 1 FU
  \item[] \textbf{ROB Entries:} 64
  \item[] \textbf{Starting Register Values:} R1=12, R2=32, F20=3.0
  \item[] \textbf{Starting Memory Values:} Mem[4]=3.0, Mem[8]=2.0, Mem[12]=1.0, Mem[24]=6.0, Mem[28]=5.0, Mem[32]=4.0
\end{enumerate}

The results of changing the issue width between 1,2,3, and 4 can be seen in figures \ref{fig:tc_iw1}, \ref{fig:tc_iw2}, \ref{fig:tc_iw3}, and \ref{fig:tc_iw4}. The main findings are that increasing issue width cannot increase the cycle of the final commit, however it can increase the cycle of intermediate commits. This is due to the way pipelining is implemented. Since EXE comes before MEM, instructions which do not require MEM will perform the WB step first since they are put into the results buffer during the |exe(...)| function call. Since the first instrution is a load operation, if non load/store instructions finish the EXE step on the same cycle that it finishes its MEM step, the non load/store instructions are placed into the results buffer first. This occurs when the issue width is 1, 3, and 4. Addi instructions finish the EXE stage on the same cycle which instruction 1 finishes its MEM stage. Since the Addi instructions (specifically their results) are placed into the results buffer first, they perform the WB stage first. Since only one instruction can perform the WB stage at one time, this means the first instruction has to wait for a later cycle. We can see by looking at \ref{fig:tc_iw2} that an issue width of 2 avoids this, since instruction 6 finishes before cycle 7 (when instruction 1 finishes its MEM stage), and instructions 10 and 11 are not issued quickly enough to finish on cycle 7, the first instruction can perform the WB stage in the cycle directly after it finishes its MEM step.

\subsection{test\_case2.txt}
In this case we stress test all portions of the o3 simulator to make sure that everything is working correctly. In total there are 73 instructions issued, memory loads and stores, all FUs and instruction types are used. The hardware configuration is given like so:
\begin{enumerate}[nosep, wide, labelindent=0pt]
  \item[] \textbf{Int. Adder:} 2 RS, 1 Cycle in EX, 1 FU
  \item[] \textbf{FP Adder:} 2 RS, 3 Cycles in EX, 1 FU
  \item[] \textbf{FP Mult.:} 2 RS, 15 Cycles in EX, 1 FU
  \item[] \textbf{Load/Store:} 3 RS, 1 Cycle in EX, 1 Cycles in Mem, 1 FU
  \item[] \textbf{ROB Entries:} 28
  \item[] \textbf{Starting Register Values:} R4=10, R5=3, R15=2, F1=2.0, F2=3.0, F3=4.0, F4=5.0, F5=6.0, F6=7.0, F7=8.0
  \item[] \textbf{Starting Memory Values:} Mem[0]=10.0, Mem[4]=20.0, Mem[8]=30.0, Mem[12]=40.0
\end{enumerate}

As the outputs are extremely long, I have included the output for an issue width of 1 and 4 in the Appendix sections \ref{sec:A1} and \ref{sec:A2} respectively. In this example again we can see that similarly to the previous test case, increasing the issue width allows for faster execution. With an issue width of 1 execution takes 130 cycles, whereas with an issue width of 4 execution takes only 105 cycles while resulting in the same final register and non-zero memory values.
